Existing skills passport/record-keeping mechanisms have digitized basic records, but validation 
and verification processes remain manual and relatively slow. 
The TOR identifies slow verification cycles as a potential factor in Pakistani migrant workers

immutably anchored.

3.4 Specific Technical Security Measures 
The technology solution is required to incorporate multiple security layers. 
A. Cryptographic Ledger Security & Decentralized Identity 
A.1 Asymmetric Key Cryptography 
The system must use public-key cryptography, including: 
 ECDSA  
 Ed25519  
Each authorized testing point is to possess a secure private key for signing credentials. 
Corresponding public keys are registered on the ledger as Decentralized Identifiers (DIDs). 
A.2 Hashing & Blockchain Anchoring 
Raw personal/credential data is not to be written directly to the blockchain. 
Instead: 
1. Skill passport metadata is processed.  
2. A unique SHA-256 cryptographic hash is generated.  
3. Only the hash is anchored to the Polygon network.

This is intended to prevent reverse-engineering of sensitive information through inspection of the 
public ledger.

1. Introduction
1.1 Purpose
This Software Design Description (SDD) translates the requirements defined in the National Skills Passport 
(NSP) System Software Requirements Specification (SRS v2.1) into a concrete, implementation-ready  
design. It describes the system's architecture, data model, component-level design, behavioral logic, and 
human–computer interfaces, using the approved diagram set (use case diagrams, sequence diagrams,  
state diagrams, sitemaps, and user-flow diagrams) as the authoritative source for design decisions. This  
document is intended to guide development, QA, and security review, and to serve as the single design  
reference alongside the SRS.
This SDD follows a structure consistent with the IEEE 1016 Software Design Description standard, adapted 
to the modular-monolith architecture and blockchain-anchored credentialing domain of the NSP System.
1.2 Scope
The design covers the complete NSP System: three client applications (Issuer Portal, Worker Mobile  
Wallet, Verifier DApp), four backend domain modules within a single modular-monolith application (Auth 
& Identity, Candidate Assessment, Blockchain Minting & Ledger, Public Verification), the smart-contract  
minting layer on the Polygon Layer-2 network, and the supporting AWS cloud infrastructure. The design  
addresses the full credential lifecycle: candidate enrolment, assessment scoring, two-tier approval, signed 
minting, wallet activation, and public verification, including offline-first data capture and administrative  
revocation.

2. System Overview
2.1 System Context
The NSP System is a new, self-contained, turnkey platform that replaces slow, manual, paper-based skills-
verification workflows with an instantly and permanently verifiable digital credential. A blockchain-based 
institutional trust layer underlies the platform: once a testing centre records and approves an assessment 
grade, the resulting credential is minted through a smart contract and cryptographically anchored, so that 
any subsequent tampering with the off-chain record is mathematically detectable.
The credential lifecycle proceeds through five stages, which anchor the entire design of this document:
• Stage 1 — Physical Skills Assessment: the candidate is tested in person at a testing hub.
• Stage 2 — Tester + Superintendent Approval: the score is entered and approved on the Issuer 
Portal through a two-role sign-off.
• Stage 3 — Signed Minting: the approved record is signed client-side by the Center Superintendent 
using the hub's private key, then submitted to the smart contract, which verifies the signature and 
mints the credential, anchoring only its SHA-256 hash.
• Stage 4 — Worker's Mobile Wallet: the wallet renders a scannable QR code and the digital 
credential for the candidate.
• Stage 5 — Employer Verification: the employer scans the QR; the system matches the off-chain 
data against the on-chain hash and returns a verification result.
2.2 Design Goals & Objectives
• Zero-PII blockchain policy: personal data is never written on-chain — only SHA-256 digests are 
anchored.
• Open standards throughout (W3C VC, Blockcerts, public Layer-2 ledgers) to avoid vendor lock-in 
and recurring licensing costs.
• Offline-first field data capture, tolerant of intermittent connectivity at remote testing hubs.
• Strong identity assurance: MFA on every login, NADRA CNIC verification at enrolment, device-
fingerprint-bound sessions.
• Auditable, tamper-evident workflow at every stage, from authentication through minting to 
revocation.
• A single deployable modular-monolith application that keeps operational simplicity while 
preserving clean domain boundaries for future decomposition.

3. Design Considerations
3.1 Assumptions & Dependencies
• Reliable, if intermittent, 4G connectivity is available at or near each of the 5 hubs.
• A gas-fee wallet is pre-funded in MATIC/POL to cover all 300 planned mint transactions.
• Testing-hub locations and personnel are confirmed and onboarded per the agreed roadmap 
(Weeks 5–6).
• NADRA CNIC values are supplied by candidates at enrolment and never transmitted in raw form 
beyond the Candidate Assessment module boundary.
• Multisig approvers for smart-contract admin authority are designated and available before mainnet 
deployment.
• A national digital-law / data-protection compliance audit is commissioned in Year 2 of operations.
3.2 Design Constraints
• Zero-PII blockchain policy — no personal data may ever be written on-chain, only SHA-256 digests.
• Open, license-free standards only (W3C VC, Blockcerts, public L2 ledgers) to avoid vendor lock-in 
and recurring software licensing costs.
• API rate limiting fixed at 60 requests/minute/IP across all public and authenticated endpoints.
• All 5 field laptops must have USB storage ports disabled and run managed EDR.
• Verifier DApp must remain free-of-charge permanently for external employers.
• Smart-contract upgrade authority must require multisig approval — no single administrator may 
act alone.
3.3 Architectural Style Rationale
The platform follows a modular monolith architecture: a single Node.js/Express application internally  
organized into four domain modules — Auth & Identity, Candidate Assessment, Blockchain Minting &  
Ledger, and Public Verification — each with a clearly defined internal interface and its own PostgreSQL  
schema within one shared database. Modules communicate via in-process calls and an internal event bus 
for asynchronous flows (for example, approval-triggered minting); no module reaches directly into  
another module's schema.
This style was chosen over a microservices decomposition because the pilot scope (300 credentials across 
5 hubs) does not justify the operational overhead of independently deployed services, while the schema-
per-module boundary preserves a clean migration path to microservices if the platform scales beyond the 
pilot. All external traffic enters through a single AWS API Gateway / WAF layer before being routed to the 
application.

4.2 Deployment Architecture
The system deploys within a single AWS account and VPC, split into a public subnet (NAT Gateway, WAF, 
Application Load Balancer) and a private subnet (backend compute, RDS PostgreSQL, ElastiCache Redis,  
Secrets Manager). The backend runs as containerized ECS/Fargate tasks behind the load balancer, with  
outbound-only access to external services (NADRA verification API, the Polygon RPC provider, and the  
mobile app stores). Frontend builds for the Issuer Portal and Verifier DApp are served from S3 via  
CloudFront; the Worker Mobile Wallet is distributed as a native app. GitHub Actions drives CI/CD,  
deploying the backend and each frontend independently within the same pipeline family. CloudWatch,  
fed by VPC flow logs, provides centralized monitoring.

6. Detailed (Component-Level) Design
This section elaborates the design of each of the four backend modules and the three client applications, 
tracing each design decision to the functional requirement(s) it satisfies (FR-xxx-nn, as defined in the SRS) 
and to the corresponding sequence diagram from the approved diagram set.
6.1 Auth & Identity Module (auth schema)
Primary responsibility: user management, multi-factor authentication (MFA), role-based session token  
issuance, and testing-hub device authorization.
Design Responsibilities
• FR-AUTH-01: Enforce dual-factor authentication (TOTP or SMS OTP) for every login, with no opt-
out.
• FR-AUTH-02: Issue RS256-signed OAuth 2.0 JWT access tokens (15-minute expiry) with a rotating 
refresh token.
• FR-AUTH-03: Restrict API access by role (Trade Tester, Center Superintendent, Super 
Administrator), re-validated within each module.
• FR-AUTH-04: Validate device fingerprints so connections originate only from authorized, EDR-
secured hub laptops.
• FR-AUTH-05: Allow a Super Administrator to instantly revoke any active session.
• FR-AUTH-06: Lock an account after 5 consecutive failed login attempts.
• FR-AUTH-07: Log every authentication event (success, failure, MFA challenge, session revocation) 
with timestamp, IP, and device fingerprint.
• FR-AUTH-08: Provide MFA recovery via ten single-use backup codes (stored as salted hashes) and 
Super Administrator-assisted reset after out-of-band identity verification.
Design Detail
The login sequence (Figure 5) is a two-step challenge: password verification followed by MFA verification. 
On the fifth consecutive failed password attempt the account is locked (FR-AUTH-06) and the failure is  
logged. Once the password is valid, the portal presents the MFA challenge screen; on successful TOTP/SMS 
verification, the module captures the device fingerprint and IP address (FR-AUTH-04), inserts a session row 
with a hashed refresh token, and issues a 15-minute RS256 JWT access token plus a rotating refresh token 
(FR-AUTH-02). Every branch of this flow — success, failure, lockout — writes an immutable audit-log entry 
(FR-AUTH-07).

6.2 Candidate Assessment Module (candidate schema)
Primary responsibility: candidate profile intake, assessment record entry, PII anonymization via blind salt 
hashing, and off-chain media handling.
Design Responsibilities
• FR-CAND-01: Support candidate enrolment for 60 candidates per hub across the 5 KP testing points

• FR-CAND-02: Generate pre-signed AWS S3 (TLS 1.3) upload URLs so photographs transfer directly

• FR-CAND-02A: Verify each candidate's CNIC against the NADRA verification service during 
enrolment before any assessment can be recorded.
• FR-CAND-03: Apply a unique, dynamic cryptographic salt to each candidate's CNIC before hashing, 
isolating the raw CNIC from downstream services.
• FR-CAND-04: Ingest encrypted, browser-cached assessment queues from the Issuer Portal

• FR-CAND-05: Restrict score submission to Trade Testers and record approval to Center 
Superintendents, enforced via the status state machine.
• FR-CAND-06: Prevent duplicate enrolment via the deterministic cnic_dedup_hash (fixed-key 
HMAC), distinct from cnic_salted_hash.
• FR-CAND-07: Allow a Center Superintendent to reject a submitted record with a mandatory 
rejection_reason, returning it to DRAFT.
• FR-CAND-08: Emit an APPROVED domain event that the ledger module subscribes to, via the 
internal event bus, for automatic minting-queue enqueue.

6.3 Blockchain Minting & Ledger Module (ledger schema)
Primary responsibility: structuring W3C Verifiable Credentials, running SHA-256 hash operations,  
submitting signed mint requests to the Polygon smart contract, and tracking revocation states.
Design Responsibilities
• FR-LEDG-01: Compile approved assessment records into W3C Verifiable Credential and Blockcerts 
JSON formats.
• FR-LEDG-02: Generate a single SHA-256 hash digest from the complete W3C credential payload for 
blockchain anchoring.
• FR-LEDG-03: Relay client-signed mint requests to the smart contract's mint function via ethers.js, 
drawing gas fees from a single pre-funded gas wallet; the backend never has access to hub private 
keys.
• FR-LEDG-04: Store transaction receipts, block numbers, contract addresses, and transaction 
hashes, keeping all raw PII off-chain.
• FR-LEDG-05: Allow Super Administrators to set a credential's off-chain revocation status without 
altering the anchored transaction, hash, or minting record.
• FR-LEDG-06: Automatically retry failed mint transactions (bounded by retry_count) and surface 
persistent failures to Super Administrators.
• FR-LEDG-07: Register each hub's public key as a DID; the private key is generated once at hub setup 
and held only in the Center Superintendent's browser (IndexedDB, passphrase-protected).
• FR-LEDG-08: Sign each credential using asymmetric cryptography (ECDSA or Ed25519) bound to the 
issuing hub's DID before minting.
• FR-LEDG-09: Have the smart contract verify the submitting hub's signature against its registered 
DID public key before minting, rejecting failed verifications.
• FR-LEDG-10: Require multisig approval for any smart-contract upgrade — no single individual may 
unilaterally alter contract logic.
6.3.1 Review, Approve, Sign & Mint Credential
Figure 10 is the most critical sequence in the system, spanning the Issuer Portal, browser IndexedDB, Auth 
Module, Candidate Assessment Module, the internal event bus, the Blockchain Minting & Ledger Module,

computes its SHA-256 digest (FR-LEDG-02), inserts QUEUED rows into minting_queue and credentials, and

contract verifies the hub's signature against its registered DID before minting (FR-LEDG-09); on success the 
transaction hash and block number are recorded and both the credential and assessment record are  
marked MINTED. On signature failure or a failed transaction, the queue entry is marked FAILED, retried

Primary responsibility: free public lookup, off-chain metadata retrieval, live hash reconciliation against the

7. Behavioral Design — State Dynamics
This section formalizes the four state machines that govern the credential lifecycle. Each state machine  
corresponds directly to an ENUM status field in the data design (Section 5) and to transitions already  
traced through the sequence diagrams in Section 6.
7.1 Assessment Record State Machine
Governs assessment_records.status. A record starts as Draft, moves to Submitted when the Trade Tester 
submits it (FR-ISS-03), and from Submitted either to Approved (superintendent approves and signs, FR-ISS-
04) or to Rejected (superintendent rejects with a reason, FR-CAND-07). A Rejected record is system-auto-
returned to Draft for correction. An Approved record transitions to Minted only once the Ledger module 
asynchronously confirms the mint (FR-CAND-08).
Figure 13. Assessment record state machine: Draft → Submitted → Approved/Rejected → Minted.
7.2 Minting Queue State Machine
Governs minting_queue.status. An Approved record enqueues as Queued; the signed request is relayed  
via ethers.js and moves to Broadcasted (FR-LEDG-03). The smart contract then either verifies the signature 
and mints, moving the entry to Confirmed (FR-LEDG-09), or the transaction fails, moving it to Failed. Failed 
entries auto-retry back to Broadcasted up to a bounded retry_count (FR-LEDG-06); once retries are  
exhausted, the entry is flagged for ManualIntervention by the Super Administrator.

10. Non-Functional Design
The following non-functional requirements from the SRS directly shaped the architectural and component 
design decisions in Sections 4–6. They are restated here as design constraints that any implementation  
must satisfy and any test plan must verify.
10.1 Security, Cryptography & Privacy
• NFR-SEC-01: TLS 1.3 in transit; AES-256 at rest across databases, S3 buckets, and client-side caches.
• NFR-SEC-02: Asymmetric key signing (ECDSA or Ed25519); public identities managed as DIDs.
• NFR-SEC-03: Zero-PII ledger policy — names, CNIC, and photographs remain off-chain; only SHA-
256 digests are anchored.
• NFR-SEC-04: All five hub laptops run centrally managed EDR with USB storage ports blocked.
• NFR-SEC-05: Backend communication exclusively over secure REST APIs using OAuth 2.0 
tokenization.
• NFR-SEC-06: Independent security review of the minting contract and its multisig admin 
configuration prior to mainnet deployment.
10.2 Performance, Throughput & Rate Limiting
• NFR-PER-01: Public credential lookups complete and display within 2.0 seconds under normal 
conditions.
• NFR-PER-02: API Gateway rate limits capped at 60 requests/minute/IP.
• NFR-PER-03: Blockchain operations execute on Polygon L2 to keep confirmation times under 5 
seconds.
10.3 Infrastructure, Availability & Resilience
• NFR-INF-01: Application runs in isolated AWS VPC subnets behind NACLs and a WAF.
• NFR-INF-02: RDS PostgreSQL runs multi-node failover with automated backups.
• NFR-INF-03: Operational availability maintained across a 24-month horizon.
• NFR-INF-04: Field applications implement a secure, encrypted offline queue that auto-synchronizes 
on reconnect.
10.4 Standards Compliance, Licensing & SLA
• NFR-SLA-01: Open standards only (W3C VC, Blockcerts) — no vendor lock-in, no recurring licensing 
fees.
• NFR-SLA-02: Verifier DApp remains permanently free for external employers and verification 
agencies.
• NFR-SLA-03: Digital-law and data-protection compliance audit during Year 2.
• NFR-SLA-04: 6-month extended code warranty followed by an 18-month paid SLA.

13. Glossary of Terms
Table 14. Glossary
Term Meaning
Blind Salt Mapping Combining a per-record cryptographic salt with a CNIC before hashing, so the same CNIC 
never produces the same hash twice and cannot be reverse-engineered from the ledger.
Credential Anchoring Writing a SHA-256 hash of a credential's contents into the blockchain via the minting 
smart contract, so later tampering with the off-chain copy is detectable.
Modular Monolith
A single deployable application internally organized into independent domain modules, 
each with its own schema and interface, communicating via in-process calls and an 
internal event bus rather than network calls between separate services.
Proxy Contract An upgradeable smart-contract pattern where a fixed address delegates its logic to a 
replaceable implementation contract, controlled by a separate admin authority.
Multisig Multi-signature authorization — an action requires approval from more than one 
designated party, so no single individual can act alone.
Gas Wallet A blockchain wallet pre-funded with network currency (MATIC/POL) used to pay 
transaction fees for minting credentials.
Off-Chain Storage Conventional encrypted database/object storage (PostgreSQL, S3) holding data that is 
never written to the blockchain.
Verifiable Credential (VC) A W3C-standardized, cryptographically signed digital claim that can be independently 
verified without contacting the original issuer.

14.  Glossary  of  Terms 
Term Meaning Blind  Salt  Mapping  Combining  a  per-record  cryptographic  salt  with  a  CNIC  before  hashing,  so  the  same  CNIC  never  produces  the  same  hash  twice  and  cannot  be  reverse-engineered  from  the  ledger  Credential  Anchoring  Writing  a  SHA-256  hash  of  a  credential's  contents  into  the  blockchain,  via  the  minting  smart  contract,  so  any  later  tampering  with  the  off-chain  copy  is  detectable  Modular  Monolith  A  single  deployable  application  internally  organized  into  independent  domain  modules,  each  with  its  own  schema  and  interface,  communicating  via  in-process  calls  and  an  internal  event  bus  rather  than  network  calls  between  separate  services  Proxy  Contract  An  upgradeable  smart-contract  pattern  where  a  fixed  address  delegates  its  logic  to  a  replaceable  implementation  contract,  controlled  by  a  separate  admin  authority

Multisig  Multi-signature  authorization  —  an  action  requires  approval  from  more  than  one  designated  party,  so  no  single  individual  can  act  alone  Gas  Wallet  A  blockchain  wallet  pre-funded  with  network  currency  (MATIC/POL)  used  to  pay  transaction  fees  for  minting  credentials  Off-Chain  Storage  Conventional  encrypted  database/object  storage  (PostgreSQL,  S3)  holding  data  that  is  never  written  to  the  blockchain  Verifiable  Credential  (VC)  A  W3C-standardized,  cryptographically  signed  digital  claim  that  can  be  independently  verified  without  contacting  the  original  issuer
